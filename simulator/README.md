# GNSS time-delay simulator (faithful, fast, SLURM-ready)

This is the working simulator for the DSP paper revision. It is built **from the
original code** (`DelayEstimation.py`, which produced `results.dat`) and kept
**numerically faithful** to it, while being fast enough for large Monte-Carlo
campaigns on SLURM.

## Files
- `DelayEstimation.py` — the ORIGINAL paper code (PyTorch + `bayes_opt`). Source
  of truth; `results.dat` was generated by it. Kept for reference/validation.
- `DelayEstimation_blind_methods.py`, `DelayEstimation_v0.py` — older variants.
- `sim_fast.py` — **`FastDelaySim`**: efficient restructuring of the original.
  Same forward (`signalModel3`, calibration error `A = A_D + sqrt(eps/2) e^{jφ}`),
  same Bayesian optimizer (`bayes_opt`, GP+EI + domain reduction, init=2/n_iter=60),
  same ESPRIT+LSKRF, same **global** L-BFGS-B refinement, same mode-2 LS residual
  objective. Speedup: precomputes `Qw` (one SVD) + a fine signature dictionary
  `CQw_dict = Qwᴴ C(grid)` and the BO/refine objective is a cheap interpolation
  instead of rebuilding `genCQw` every evaluation (~2.5× faster: 4.4 vs 11 s/MC;
  the remaining cost is the `bayes_opt` GP itself). Returns LSKRF, LSKRF+Ref, BO,
  BO+Ref. `bo_engine` flag selects `"bayesopt"` (default, faithful) or `"botorch"`.
- `botorch_bo.py` — BoTorch GP+EI BO prototype (GPU-capable). VALIDATED AS NOT
  matching `bayes_opt` (bayes_opt's sequential domain reduction is decisive), so
  `bayesopt` is the default. Revisit only on a GPU node + with domain reduction.
- `runner_fast.py` — auditable, resumable SLURM campaign runner: scenario =
  cartesian product of `grid_fast.yaml`; content hash → output dir; `config.yaml`
  audit; `results.csv` checkpoint every N; resume from first missing `mc_index`;
  `seed = base_seed + mc_index`.
- `grid_fast.yaml` — the campaign grid (cn0, angle_diff, delay_diff, epsilon, xi).
- `submit_fast.sbatch` — SLURM array launcher.

## Run a campaign
```bash
cd simulator
python runner_fast.py --list          # scenario count (= SLURM array size)
python runner_fast.py 0               # run one scenario locally
sbatch submit_fast.sbatch             # full array on the cluster (set --array)
```
Outputs go to `results_fast/<hash>/results.csv` (+ `config.yaml`). Re-running
resumes; different `bo_engine`/params get different hashes.

Then aggregate into the paper's figure CSVs:
```bash
python aggregate_fast.py results_fast --to-paper
```
This writes `summary_fast.csv` (one row per scenario, per-method mean/median/
outlier-rate) and the wide figure CSVs in `figure_csv/` (same columns as
`paper/plots/data_revision/*.csv`); `--to-paper` copies them into the paper repo.
Edit the reference operating point (cn0/dphi/dtau/eps/xi) at the top of
`aggregate_fast.main` to choose the slice each figure shows.

## Validation vs the original (results.dat)
`FastDelaySim` reproduces `results.dat` statistics (LSKRF / BO / BO+Ref medians
and outlier rates) within Monte-Carlo noise — see `validation_vs_original.csv`
(generated by the validation script). The `bayes_opt` engine is the faithful one;
`botorch` does not match and is kept only as a GPU prototype.

## GPU
`FastDelaySim` auto-detects `cuda`/`cpu` (`self.device`). The torch forward /
objective can move to GPU, but the per-MC bottleneck is the CPU `bayes_opt` GP,
so the practical scaling is SLURM CPU parallelism (each MC/scenario is
independent). A full GPU port must be validated on an actual GPU node.
